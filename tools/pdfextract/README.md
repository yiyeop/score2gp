# pdfextract — 벡터 악보 PDF 추출 프로토타입

Phase 1의 알고리즘을 빠르게 다듬기 위한 **Python 프로토타입**이다.
휴리스틱이 안정되면 Rust(`src-tauri`)로 옮겨 앱에 내장할 계획이라,
여기서는 PyMuPDF의 편의를 빌려 좌표 계산 로직에만 집중한다.

## 왜 OMR이 아닌가

시중 기타 악보 PDF는 대개 Guitar Pro·Finale에서 내보낸 벡터 PDF다.
음표는 이미지가 아니라 **음악 폰트의 글리프**이고, 오선·TAB·마디선은 벡터 선이다.
그래서 이미지 인식 없이 좌표만으로 구조를 복원할 수 있다.
자세한 배경은 최상위 `README.md`의 "Phase 1 방향 전환" 절 참고.

## 실행

```bash
python3 -m venv .venv && .venv/bin/pip install pymupdf

# 마디별 TAB 내용을 텍스트로 확인
.venv/bin/python dump.py "악보.pdf" 1

# 프렛+길이를 합친 최종 결과 — [1/8 5현7] 형태
.venv/bin/python dump_notes.py "악보.pdf" 1

# 인식 결과를 원본 위에 겹쳐 그려 PNG로 확인 (가장 확실한 검증법)
.venv/bin/python overlay.py "악보.pdf" 1 out.png

# 리듬 판정을 자동 검증 — 마디 길이 합이 박자와 맞는지 전 페이지 검사
.venv/bin/python verify.py "악보.pdf"

# 곡 전체를 조립해 요약 — 제목·템포·악기·마디 수
.venv/bin/python dump_song.py "악보.pdf"

# PDF → Guitar Pro 파일 변환 (최종 산출물)
.venv/bin/python convert.py "악보.pdf" out.gp5
```

앱의 **PDF 변환** 버튼도 이 `convert.py`를 부른다. 앱은 `tools/pdfextract/.venv`를
먼저 찾고 없으면 시스템 `python3`을 쓰므로, 위 명령으로 가상환경을 만들어 두면
앱에서도 바로 동작한다.

### 품질은 두 지표로 자동 측정한다

악보를 눈으로 대조하는 건 느리고 놓치기 쉬워서, `verify.py`가 전 페이지를
훑으며 두 가지를 잰다. 휴리스틱을 고칠 때마다 이 수치로 회귀를 확인한다.

- **마디 길이 합** — 리듬을 제대로 읽었다면 4/4 마디의 합은 정확히 4박이다.
- **프렛 결합률** — 쉼표가 아닌 소리에 짚는 자리가 붙었는지. 오선보는 읽었는데
  TAB을 못 붙였거나(밴딩 목표음 등) 그 반대인 경우가 여기서 드러난다.

## 현재 상태

검증에 쓴 샘플 두 종은 제작 도구가 서로 달라 처리 방식도 갈린다.

| | 광인들 (Guitar Pro) | 사랑하게 될 거야 (Finale) |
|---|---|---|
| 음악 폰트 | GPBravura (SMuFL 표준) | Maestro (레거시 인코딩) |
| TAB 줄 간격 | 6.38pt | 4.60pt |
| 마디선 | 보표마다 따로 그림 | 오선~TAB 한 줄로 관통 |
| 구성 | Lead/Rhythm 각 오선+TAB | 보컬(오선만) + Gt.1/Gt.2 |

**되는 것**

- 오선(5줄)·TAB(6줄) 판별과 위치 검출
- 오선과 TAB을 한 악기로 짝짓기 (보컬처럼 TAB 없는 보표도 구분)
- 마디선 검출 (두 가지 그리기 방식 모두)
- TAB 프렛·현 추출, 두 자리 프렛(10~24) 병합, 데드 노트(X)
- 같은 위치의 표시를 화음으로 묶기
- 음길이 판정 — 머리 모양 + 빔 개수 + 플래그 + 점 + 쉼표
- 폰트 계열 추상화 (`fonts.py`) — SMuFL과 레거시(Maestro)를 같은 로직으로 처리
- **프렛 + 길이 결합** — 오선보의 리듬과 TAB의 짚는 자리를 x좌표로 짝지어
  `[1/8 5현7]` 형태의 연주 가능한 데이터로 만든다
- **곡 전체 조립** (`assemble.py`) — 시스템을 나누고 페이지를 넘어 같은 악기를
  이어 붙인다. 제목·템포·악기 이름도 읽는다
- **`.gp5` 파일 생성** (`gpwrite.py`, `convert.py`) — 추출 결과를 실제 Guitar Pro
  파일로 쓴다. 광인들 샘플로 PDF → .gp5 → 앱 재생까지 확인했다
- **조율** (`tuning.py`) — `① = E♭` 표기를 읽어 현별 음높이를 맞춘다.
  표기가 없으면 표준 튜닝을 쓴다
- **주법·톤** (`annotations.py`) — `P.M.` `sl.` `letring` `H`를 GP 이펙트로,
  `Distortion` `Delay` 같은 톤 지시를 음색 변경과 텍스트로 옮긴다.
  P.M.·let ring은 점선 괄호를 따라가 **구간 전체**에 적용한다

**검증 결과** (샘플 4종)

내보내는 대상인 **기타 파트 기준**이다(보컬 보표는 GP로 옮기지 않는다).

| 샘플 | 제작 도구 | 마디 길이 합 | 프렛 결합률 |
|---|---|---|---|
| 광인들 | Guitar Pro / SMuFL | **262/264 (99.2%)** | 1374/1495 (91.9%) |
| 사랑하게 될 거야 | Finale / Maestro | **172/173 (99.4%)** | **710/710 (100%)** |
| 달빛소년 | Finale / Maestro | 497/512 (97.1%) | 1161/1260 (92.1%) |
| 유다빈 ONCE | Finale / Maestro | 361/393 (91.9%) | 908/981 (92.6%) |
| 달빛소년(합성) | MuseScore / Leland | **244/244 (100%)** | **933/933 (100%)** |

오선보 음표와 TAB 숫자의 x 차이는 실측 0.5pt 안쪽이라 짝짓기 자체는 안정적이다.

수집한 샘플 4종 중 3종이 Finale이다(국내 악보 사이트가 주로 쓰는 듯).
글리프 매핑과 기둥 검출을 고치면서 23~35% → 85~97%까지 올렸다.

MuseScore 샘플은 손에 넣은 게 아니라 만든 것이다. 갖고 있던 GP 파일을
오선+TAB 쌍의 MusicXML로 내보내(`gp2xml.py`) MuseScore로 조판했다.
덕분에 **원본 GP가 정답지**가 되어 마디와 프렛을 하나하나 대조할 수 있다.

```bash
.venv/bin/python gp2xml.py "악보.gp5" out.musicxml 2 7   # 트랙 2·7
mscore -o out.pdf out.musicxml
```

**아직 안 되는 것**

- **성부가 셋 이상**이거나, 갈라도 어느 쪽도 마디 길이에 맞지 않는 경우.
  2성부는 처리한다(아래 참고).
- **못갖춘마디(pickup)** 로 시작하는 곡. 첫 마디는 4박이 아닌 게 정상인데
  검증기가 이를 오류로 센다(실제 변환에는 문제 없음).
- **밴딩의 시간 곡선** — PDF에는 도달 음정만 있고 언제 올리는지가 없어서
  '중간에 올려 끝까지 유지'하는 표준 모양으로 만든다.
- **Delay·Chorus** — GP5 믹스 테이블에 대응 항목이 없거나 강도를 알 수 없어
  음색 변경 대신 텍스트로만 남긴다. Distortion·Clean 등 음색에 대응하는 것만
  악기 변경으로 옮긴다.
- **그림으로 그린 악보의 쉼표.** 음표를 글자가 아니라 윤곽선으로 저장한
  PDF가 있다(악보바다 계열). 음표머리는 크기로 알아볼 수 있어서 읽지만
  (아래 참고), 쉼표는 모양이 제각각이라 크기만으로 못 가린다. 그래서
  그런 악보는 음과 프렛은 맞지만 마디가 짧아진다 — 쏜애플 아지랑이에서
  프렛 결합률 96.7%에 마디 길이 일치율 59.5%였다.
- **피아노 등 TAB 없는 악보.** 음높이를 오선 위치 + 음자리표 + 조표에서
  계산해야 하는데, TAB에서 현·프렛을 그대로 읽는 지금 구조와는 다른 작업이다.
- 셋잇단음표 외의 잇단음표(다섯·여섯잇단 등). 손에 있는 악보에 없어서
  근거가 없다 — 넓히면 가사나 코드 이름의 숫자에 걸릴 위험이 크다.
- 박자표는 아직 안 읽는다 (4/4로 가정).
- **드럼**. 오선만 있고 TAB이 없어서 지금 구조로는 옮길 대상이 아니다.
  GP로 넣으려면 타악기 매핑이 따로 필요하다.

## 구현 메모

직접 부딪혀서 알게 된, 다시 밟기 쉬운 함정들.

- **보표 검출은 '간격 균일성'으로 해야 한다.** 가까운 선끼리 묶으면 보표 바로 위에
  붙는 P.M. 괄호선까지 섞여 줄 수가 어긋난다. 실제로 TAB이 한 줄 밀려 잡혔다.
- **줄 수가 많은 쪽을 먼저 확정해야 한다.** 6줄 TAB 안에는 5줄짜리 균일 구간이
  반드시 들어 있어서, 편차만으로 정렬하면 TAB이 오선 두 개로 쪼개진다.
  4줄 TAB(베이스)까지 찾으려면 6 → 5 → 4 순서여야 한다.
- **4줄 TAB은 '위에 더 없는지' 확인하고 받아야 한다.** 프렛 숫자가 빽빽한
  TAB은 줄이 숫자마다 끊겨(실측 63토막, 덮인 길이 38%) 위 두 줄이 후보에서
  빠진다. 그러면 6줄 기타 TAB의 아래 네 줄만 남아 베이스로 읽히고, 조율까지
  틀리게 된다. 문턱을 못 넘은 줄도 자리는 기억해 두었다가, 같은 간격으로
  위에 줄이 더 있으면 4줄 창을 버린다.
- **두 자리 프렛은 글자가 겹쳐 그려진다.** 간격이 -0.54pt처럼 음수로 나와서
  붙임 판정에 음수 허용이 필요하다.
- **현 판정은 baseline이 아니라 글자 상자 중앙 y로 한다.**
- **마디선과 음표 기둥은 길이로 구분되지 않는다.** 기둥도 보표 높이만큼 길다.
  오선·TAB 양쪽에 같은 x로 나타나는지를 봐야 한다.
- **화음의 음표는 x가 어긋난다.** 2도 간격으로 붙은 음은 서로 겹치지 않게
  머리 하나 폭(약 4.5pt)만큼 옆으로 밀어 그린다. '같은 x'로 묶으면 화음
  하나가 둘로 쪼개져 마디 길이가 정확히 두 배가 된다.
  밀려난 음표에는 기둥이 없으므로 기둥은 화음 전체에서 찾아야 한다.
- **2성부는 '갈라서 맞아떨어질 때만' 나눈다.** 기둥 방향은 성부와 무관하게도
  바뀌므로(음 높이에 따라), 방향만 보고 나누면 멀쩡한 마디를 망가뜨린다.
  갈랐을 때 한쪽이 정확히 마디 길이가 되는 마디에만 적용했더니 Finale 샘플
  두 종이 90.9% → 95.4%, 84.5% → 89.4%가 됐고 나머지는 그대로였다.
- **성부를 쓰는 트랙은 모든 마디에 성부 2가 있어야 한다.** 일부 마디에만
  넣으면 alphaTab이 성부를 이어 붙이다 `Cannot read properties of undefined
  (reading 'beats')`로 죽는다. 빈 마디를 온쉼표로 채우는 것과 같은 이유다.
- **점(dot)은 화음 단위로 세야 한다.** 줄 위의 음표는 점이 반 칸 위로 밀리는데,
  음표마다 따로 세면 옆 음표의 점까지 자기 것으로 세어 겹점이 된다.
- **빔은 채워진 4각 폴리곤**이고, 기둥 x를 포함하며 세로로 겹치는 개수가
  그대로 음길이가 된다(1개 8분, 2개 16분). 기울어진 빔은 경계 상자가
  두꺼워지므로 상자 겹침으로 판정한다.
- **빔의 위아래 모서리를 보표 줄 후보에서 빼야 한다.** 8분음표가 이어지는
  마디에서는 이 모서리가 오선 사이 높이에 깔려, '간격이 고른 5줄'을 찾는
  눈을 흐린다. 실제로 한 페이지에서 오선이 통째로 안 잡혀 8마디가 사라졌다.
- **덧줄(ledger line)도 보표 줄로 오인된다.** 오선 위로 나간 음표마다 하나씩
  붙는데 높이가 정확히 한 칸 위라 줄 하나처럼 보이고, 음표가 많으면 덮인
  길이도 충분해진다. 그러면 5줄 오선이 6줄 TAB으로 잡혀 파트가 통째로
  어긋난다. 보표의 줄들은 함께 그려져 시작·끝이 나란한 반면 덧줄은
  마디 안쪽에만 있어 시스템 가장자리까지 닿지 않는다 — 이걸로 가른다.
- **잇단음표는 숫자만 보고 판단하면 안 된다.** 어느 조판기든 '3'을 글자로
  찍는데, 가사·코드 이름에도 숫자가 있고 어느 음표까지 묶이는지는 표시만
  봐서는 모른다. 숫자는 묶음 **가운데 음표** 위(또는 아래)에 놓이므로 그걸로
  묶음을 고르고, 줄여본 결과가 마디 길이와 정확히 맞을 때만 받아들인다.
  TAB의 프렛도 같은 글자라서 TAB 윗줄 아래는 아예 보지 않는다.
- **프렛은 자릿수가 아니라 '값'으로 막아야 한다.** 빠른 패시지에서는 이웃한
  프렛 숫자 사이 간격이 두 자리 수 내부 간격만큼 좁아진다. 실측하면 `9`와
  `11` 사이가 1.33pt인데 `11` 안쪽은 -0.54pt로, 자리 배치만으로는 갈리지
  않는다. 두 자리로 제한하는 것만으로는 `9 11 9`가 `91 1 9`가 된다 —
  91프렛짜리 기타는 없으므로, 합쳐서 24를 넘으면 원래 두 음이었다고 본다.
- **밴딩 목표음을 숫자로 적는 악보가 있다.** 원래 음 한 줄 위에 화살표로
  이어 그리는데, 그걸 치는 음으로 세면 있지도 않은 음이 들어가고 박자도
  넘친다. 화살표와 x가 겹치는 숫자는 목표음이다. 거를 때는 **두 자리 수를
  합친 뒤**에 해야 한다 — 합치기 전에 거르면 화살표에 걸친 글자만 빠져서
  `14`가 `4`로 남는다.
- **시스템은 왼쪽 괄호로 나눠야 한다.** 다른 단서는 전부 실패한다.
  세로 간격 — 시스템 안쪽 간격이 시스템 사이보다 넓은 경우가 있다.
  마디선 위치 — 반복이 많은 곡은 여러 시스템의 마디선이 거의 같은 자리에 온다.
  악기 구성의 주기 — 쉬는 악기의 보표를 빼고 찍는 악보가 있어 주기가 깨진다.
  괄호를 찾을 때는 **보표가 시작하는 x를 모두 기준으로** 삼아야 한다.
  첫 시스템은 악기 이름 자리 때문에 들여쓰기돼 괄호도 그만큼 밀려 있어서,
  페이지 전체의 최소 x 하나로 찾으면 첫 시스템을 통째로 놓친다.
- **악기 자리는 'TAB 있는 것 중 몇 번째'로 세야 한다.** 쉬는 악기의 보표를
  빼고 찍으면 시스템마다 보표 수가 달라져서, 단순히 위에서 몇 번째로 세면
  기타 파트가 시스템을 넘어가며 어긋난다.
- **보표를 뺀 자리는 온쉼표로 채워야 한다.** 위 규칙으로 자리는 맞췄어도,
  빠진 마디를 그냥 건너뛰면 그 악기의 악보가 곡보다 짧아지고 다시 나오는
  자리부터 전부 앞으로 당겨진다. ONCE는 Gt.2가 50마디, Gt.1이 107마디로
  나왔는데 실제 곡은 131마디다 — 같이 연주하면 박이 맞지 않는다.
  채우고 나니 세 파트가 모두 131마디로 맞았다(88.9% → 91.9%).
  다만 **곡 중간에 처음 나오는 악기까지 앞을 채우려 하면 안 된다.** 유령
  트랙(보표를 한 번 잘못 잡아 생긴 것)까지 부풀어 멀쩡한 파트가 늘어난다.
- **마디선은 시스템 전체의 합의로 정한다.** 여러 보표에서 함께 발견된 x만
  남기면, 한 보표에만 있는 음표 기둥을 걸러낼 수 있다. TAB 없는 보컬 보표는
  기둥이 마디선으로 오인되기 쉬워 특히 효과가 크다.
- **주석의 세로 범위는 이웃 악기와의 중간선으로 잘라야 한다.** 넉넉히 잡으면
  아래 시스템의 지시까지 끌어온다. 실제로 Rhythm 2마디에 다음 시스템의
  `Distortion`이 붙어, 원래 있어야 할 `Delay`를 덮어쓰고 있었다.
- **P.M.·let ring은 점선 괄호가 구간을 나타낸다.** 괄호는 글자 바로 위
  가로선으로 그려지고, 같은 줄에 여러 개가 있어도 사이가 뚜렷이 벌어져
  있어서 글자 오른쪽에서 가장 먼저 시작하는 선을 고르면 된다.
  구간 처리를 넣으니 팜뮤트가 74 → 466개가 됐다.
- **기둥 없는 검은 음표머리는 음이 아니다.** 밴딩을 '원음 + 목표음 + 되돌린
  음'처럼 여러 머리로 그리는 악보가 있는데, 그 머리들은 기둥 없이 찍힌다.
  검은 머리에 기둥이 없는 건 정상적인 음표일 수 없으니 시간도 차지하지
  않는다. 길이를 더하면 마디가 부풀어서, 광인들 솔로의 111·112·113·118마디가
  모두 5~6박으로 읽혔다. 빼고 나니 넷 다 정확히 4박이 됐다(97.7% → 99.2%).
  프렛을 못 찾은 머리에만 적용하므로, 기둥 검출이 실패한 진짜 음표를 잘못
  지울 위험은 낮다 — 진짜 음표라면 TAB에 숫자가 있다.
- **밴딩 표기는 목표음 위에 적힌다.** 그런데 그 목표음은 시작음에 병합돼
  사라지므로, 가장 가까운 음을 고르면 뒤쪽 엉뚱한 음(데드 노트 등)에 붙는다.
  표기보다 **앞에 있는, 실제로 칠 수 있는 마지막 음**이 밴딩의 시작음이다.
- **기둥은 음표머리 중심과 세로로 어긋날 수 있다.** 리듬 슬래시(/)는 글리프
  기준점이 기둥 닿는 자리보다 0.7pt 위에 있어서, 딱 맞게 보면 기둥을 통째로
  놓치고 전부 4분음표로 읽힌다. 세로 허용치를 5.5pt로 넓히자 Finale 샘플이
  67% → 93%, 51% → 70%가 됐다. **다성부보다 이쪽이 훨씬 큰 원인이었다.**
- **보표가 하나뿐인 시스템은 마디선을 걸러야 한다.** 서로 대조할 상대가 없어
  음표 기둥이 마디선으로 섞여 들어오고, 폭 13~40pt짜리 조각 마디가 생긴다
  (정상은 100~160pt). 다른 마디에 비해 터무니없이 좁은 구간을 만드는 선을
  걷어내면 ONCE가 80% → 84.5%가 된다.
- **음표머리는 글자가 없어도 크기로 찾을 수 있다.** 모든 기호를 윤곽선으로
  저장한 PDF는 글리프 코드가 없지만, 음표머리만은 크기가 규칙적이다 —
  오선 간격으로 나누면 실측 1.18×1.00(음표머리), 0.40×0.40(점),
  1.80×1.02(온음표)로 뚜렷이 갈렸다. SMuFL 코드를 붙인 가짜 글리프로
  만들어 넘기면 화음 묶기·기둥·빔·점 세기가 그대로 동작한다.
  음악 폰트가 있으면 그쪽이 훨씬 정확하므로 **없을 때만** 쓴다.
  쉼표는 만들지 않는다. 크기가 비슷한 것 중에 스트로크 표시(∨)가 섞여
  있어서(실제로 처음엔 쉼표로 착각했다) 잘못 넣으면 없는 박이 생긴다 —
  모자란 것보다 나쁘다.
- **레거시 음악 폰트는 코드값에 규칙이 없다.** Maestro는 음표머리가 `œ`,
  플래그가 `J`·`j`, 8분쉼표가 `‰` 하는 식이라 추측으로는 못 맞춘다.
  글리프를 하나씩 잘라 한 장에 모아 눈으로 확인해야 한다
  (`scratchpad/glyphsheet.py`). 플래그 두 개를 찾은 것만으로 달빛소년이
  35% → 64%가 됐다.
- **코드 반주 악보에는 리듬 슬래시(/)가 많다.** '직전 화음을 한 번 더'라는
  표기라 박자는 차지하지만 TAB에 프렛이 없다. 음표로 세지 않으면 마디가
  모자라고, 세기만 하고 화음을 안 채우면 소리가 안 난다. 둘 다 해야 한다.
- **빈 마디를 그대로 두면 재생기가 죽는다.** 쉬는 악기의 보표를 뺀 악보에서
  파트마다 마디 수가 달라지는데, 모자란 마디를 온쉼표로 채워야 한다.
- **GP는 슬라이드의 도착 프렛을 저장하지 않는다.** 같은 현의 다음 음이 곧
  도착점이라, 이어지는 음이 없는 현에 걸면 갈 곳 없는 슬라이드가 된다.
  다음 음이 같은 현에 있을 때만 걸어야 한다(151 → 102개로 걸러졌다).
