# pdfextract — 벡터 악보 PDF 추출 프로토타입

Phase 1의 알고리즘을 빠르게 다듬기 위한 **Python 프로토타입**이다.
휴리스틱이 안정되면 Rust(`src-tauri`)로 옮겨 앱에 내장할 계획이라,
여기서는 PyMuPDF의 편의를 빌려 좌표 계산 로직에만 집중한다.

## 왜 OMR이 아닌가

시중 기타 악보 PDF는 대개 Guitar Pro·Finale에서 내보낸 벡터 PDF다.
음표는 이미지가 아니라 **음악 폰트의 글리프**이고, 오선·TAB·마디선은 벡터 선이다.
그래서 이미지 인식 없이 좌표만으로 구조를 복원할 수 있다.
자세한 배경은 최상위 `README.md`의 "Phase 1 방향 전환" 절 참고.

## 실행

```bash
python3 -m venv .venv && .venv/bin/pip install pymupdf

# 마디별 TAB 내용을 텍스트로 확인
.venv/bin/python dump.py "악보.pdf" 1

# 프렛+길이를 합친 최종 결과 — [1/8 5현7] 형태
.venv/bin/python dump_notes.py "악보.pdf" 1

# 인식 결과를 원본 위에 겹쳐 그려 PNG로 확인 (가장 확실한 검증법)
.venv/bin/python overlay.py "악보.pdf" 1 out.png

# 리듬 판정을 자동 검증 — 마디 길이 합이 박자와 맞는지 전 페이지 검사
.venv/bin/python verify.py "악보.pdf"

# 곡 전체를 조립해 요약 — 제목·템포·악기·마디 수
.venv/bin/python dump_song.py "악보.pdf"

# PDF → Guitar Pro 파일 변환 (최종 산출물)
.venv/bin/python convert.py "악보.pdf" out.gp5
```

### 품질은 두 지표로 자동 측정한다

악보를 눈으로 대조하는 건 느리고 놓치기 쉬워서, `verify.py`가 전 페이지를
훑으며 두 가지를 잰다. 휴리스틱을 고칠 때마다 이 수치로 회귀를 확인한다.

- **마디 길이 합** — 리듬을 제대로 읽었다면 4/4 마디의 합은 정확히 4박이다.
- **프렛 결합률** — 쉼표가 아닌 소리에 짚는 자리가 붙었는지. 오선보는 읽었는데
  TAB을 못 붙였거나(밴딩 목표음 등) 그 반대인 경우가 여기서 드러난다.

## 현재 상태

검증에 쓴 샘플 두 종은 제작 도구가 서로 달라 처리 방식도 갈린다.

| | 광인들 (Guitar Pro) | 사랑하게 될 거야 (Finale) |
|---|---|---|
| 음악 폰트 | GPBravura (SMuFL 표준) | Maestro (레거시 인코딩) |
| TAB 줄 간격 | 6.38pt | 4.60pt |
| 마디선 | 보표마다 따로 그림 | 오선~TAB 한 줄로 관통 |
| 구성 | Lead/Rhythm 각 오선+TAB | 보컬(오선만) + Gt.1/Gt.2 |

**되는 것**

- 오선(5줄)·TAB(6줄) 판별과 위치 검출
- 오선과 TAB을 한 악기로 짝짓기 (보컬처럼 TAB 없는 보표도 구분)
- 마디선 검출 (두 가지 그리기 방식 모두)
- TAB 프렛·현 추출, 두 자리 프렛(10~24) 병합, 데드 노트(X)
- 같은 위치의 표시를 화음으로 묶기
- 음길이 판정 — 머리 모양 + 빔 개수 + 플래그 + 점 + 쉼표
- 폰트 계열 추상화 (`fonts.py`) — SMuFL과 레거시(Maestro)를 같은 로직으로 처리
- **프렛 + 길이 결합** — 오선보의 리듬과 TAB의 짚는 자리를 x좌표로 짝지어
  `[1/8 5현7]` 형태의 연주 가능한 데이터로 만든다
- **곡 전체 조립** (`assemble.py`) — 시스템을 나누고 페이지를 넘어 같은 악기를
  이어 붙인다. 제목·템포·악기 이름도 읽는다
- **`.gp5` 파일 생성** (`gpwrite.py`, `convert.py`) — 추출 결과를 실제 Guitar Pro
  파일로 쓴다. 광인들 샘플로 PDF → .gp5 → 앱 재생까지 확인했다
- **조율** (`tuning.py`) — `① = E♭` 표기를 읽어 현별 음높이를 맞춘다.
  표기가 없으면 표준 튜닝을 쓴다
- **주법·톤** (`annotations.py`) — `P.M.` `sl.` `letring` `H`를 GP 이펙트로,
  `Distortion` `Delay` 같은 톤 지시를 음색 변경과 텍스트로 옮긴다.
  P.M.·let ring은 점선 괄호를 따라가 **구간 전체**에 적용한다

**검증 결과** (샘플 4종)

| 샘플 | 제작 도구 | 마디 길이 합 | 프렛 결합률 |
|---|---|---|---|
| 광인들 | Guitar Pro / SMuFL | **258/264 (97.7%)** | **1381/1509 (91.5%)** |
| 달빛소년 | Finale / Maestro | 146/417 (35.0%) | 867/1511 (57.4%) |
| 사랑하게 될 거야 | Finale / Maestro | 62/179 (34.6%) | 391/723 (54.1%) |
| 유다빈 ONCE | Finale / Maestro | 82/358 (22.9%) | 450/1425 (31.6%) |

오선보 음표와 TAB 숫자의 x 차이는 실측 0.5pt 안쪽이라 짝짓기 자체는 안정적이다.

Guitar Pro 계열은 실용 수준이지만 **Finale 계열은 아직 낮다.** 수집한 샘플
4종 중 3종이 Finale이라(국내 악보 사이트가 주로 쓰는 듯) 여기를 올리는 것이
가장 시급하다. 원인은 아래 "Finale 계열이 어려운 이유" 참고.

**아직 안 되는 것**

- **밴딩(bend)** — Guitar Pro 샘플에 남은 오차의 주원인이다. TAB에는 짚는
  프렛만 한 번 적히는데 오선보에는 밴딩 목표음까지 음표로 그려진다.
  그래서 오선보 음표가 TAB보다 많아지고(결합률 하락), 목표음의 길이까지
  더해져 마디 합이 넘친다(길이 불일치). 벤드 화살표 글리프(`U+EB78`)와
  `full`·`1/2` 텍스트가 이미 추출되므로, 이를 보고 음표 쌍을 한 소리로
  합치면 두 지표가 함께 올라간다.
**Finale 계열이 어려운 이유**

글리프는 잘라서 눈으로 확인해 매핑을 바로잡았고(`scratchpad/glyphsheet.py`),
빔도 사각형으로 그린다는 걸 반영했다. 그래도 정확도가 낮은데, 샘플을 보면
Guitar Pro와 조판 방식이 근본적으로 다르다.

- **TAB에도 기둥과 빔이 따로 그려진다.** Guitar Pro는 TAB에 숫자만 적고 리듬은
  오선보에만 두는데, Finale은 TAB 아래에도 리듬을 그린다. 오선보 대신 TAB
  쪽 리듬을 읽는 편이 오히려 정확할 수 있다(성부 문제를 피할 수 있어서).
- **오선보에 성부가 둘인 경우가 많다.** 기타 편곡은 멜로디와 베이스를 한
  보표에 위·아래 기둥으로 나눠 적는다. 지금은 둘을 구분하지 않고 다 세어서
  마디 길이가 넘친다.
- **못갖춘마디(pickup)** 로 시작하는 곡이 있다. 첫 마디는 4박이 아닌 게
  정상이라 지금 검증기는 이를 오류로 센다.
- **밴딩의 시간 곡선** — PDF에는 도달 음정만 있고 언제 올리는지가 없어서
  '중간에 올려 끝까지 유지'하는 표준 모양으로 만든다.
- **Delay·Chorus** — GP5 믹스 테이블에 대응 항목이 없거나 강도를 알 수 없어
  음색 변경 대신 텍스트로만 남긴다. Distortion·Clean 등 음색에 대응하는 것만
  악기 변경으로 옮긴다.
- 잇단음표(셋잇단 등) 미지원.
- **쉬는 악기의 보표를 뺀 악보에서 마디 수가 어긋난다.** 조립은 인쇄된 것을
  그대로 읽으므로, 보표가 생략된 구간만큼 그 악기의 마디가 비게 된다.
  `.gp`로 내보내려면 빠진 구간을 쉼표 마디로 채워 길이를 맞춰야 한다.
  (달빛소년 138/138/138 정렬 ✓ / ONCE는 Gt.2가 48마디만 인쇄됨)
- 조율(`Tune down 1/2 step`)과 박자표는 아직 안 읽는다.

## 구현 메모

직접 부딪혀서 알게 된, 다시 밟기 쉬운 함정들.

- **보표 검출은 '간격 균일성'으로 해야 한다.** 가까운 선끼리 묶으면 보표 바로 위에
  붙는 P.M. 괄호선까지 섞여 줄 수가 어긋난다. 실제로 TAB이 한 줄 밀려 잡혔다.
- **줄 수가 많은 쪽을 먼저 확정해야 한다.** 6줄 TAB 안에는 5줄짜리 균일 구간이
  반드시 들어 있어서, 편차만으로 정렬하면 TAB이 오선 두 개로 쪼개진다.
- **두 자리 프렛은 글자가 겹쳐 그려진다.** 간격이 -0.54pt처럼 음수로 나와서
  붙임 판정에 음수 허용이 필요하다.
- **현 판정은 baseline이 아니라 글자 상자 중앙 y로 한다.**
- **마디선과 음표 기둥은 길이로 구분되지 않는다.** 기둥도 보표 높이만큼 길다.
  오선·TAB 양쪽에 같은 x로 나타나는지를 봐야 한다.
- **화음의 음표는 x가 어긋난다.** 2도 간격으로 붙은 음은 서로 겹치지 않게
  머리 하나 폭(약 4.5pt)만큼 옆으로 밀어 그린다. '같은 x'로 묶으면 화음
  하나가 둘로 쪼개져 마디 길이가 정확히 두 배가 된다.
  밀려난 음표에는 기둥이 없으므로 기둥은 화음 전체에서 찾아야 한다.
- **점(dot)은 화음 단위로 세야 한다.** 줄 위의 음표는 점이 반 칸 위로 밀리는데,
  음표마다 따로 세면 옆 음표의 점까지 자기 것으로 세어 겹점이 된다.
- **빔은 채워진 4각 폴리곤**이고, 기둥 x를 포함하며 세로로 겹치는 개수가
  그대로 음길이가 된다(1개 8분, 2개 16분). 기울어진 빔은 경계 상자가
  두꺼워지므로 상자 겹침으로 판정한다.
- **프렛은 최대 두 자리(0~24)라는 제약을 걸어야 한다.** 빠른 패시지에서는
  이웃한 프렛 숫자 사이 간격이 두 자리 수 내부 간격만큼 좁아져서,
  제약이 없으면 `12 14 12`가 `121412` 하나로 이어붙는다.
- **시스템은 왼쪽 괄호로 나눠야 한다.** 다른 단서는 전부 실패한다.
  세로 간격 — 시스템 안쪽 간격이 시스템 사이보다 넓은 경우가 있다.
  마디선 위치 — 반복이 많은 곡은 여러 시스템의 마디선이 거의 같은 자리에 온다.
  악기 구성의 주기 — 쉬는 악기의 보표를 빼고 찍는 악보가 있어 주기가 깨진다.
  괄호를 찾을 때는 **보표가 시작하는 x를 모두 기준으로** 삼아야 한다.
  첫 시스템은 악기 이름 자리 때문에 들여쓰기돼 괄호도 그만큼 밀려 있어서,
  페이지 전체의 최소 x 하나로 찾으면 첫 시스템을 통째로 놓친다.
- **악기 자리는 'TAB 있는 것 중 몇 번째'로 세야 한다.** 쉬는 악기의 보표를
  빼고 찍으면 시스템마다 보표 수가 달라져서, 단순히 위에서 몇 번째로 세면
  기타 파트가 시스템을 넘어가며 어긋난다.
- **마디선은 시스템 전체의 합의로 정한다.** 여러 보표에서 함께 발견된 x만
  남기면, 한 보표에만 있는 음표 기둥을 걸러낼 수 있다. TAB 없는 보컬 보표는
  기둥이 마디선으로 오인되기 쉬워 특히 효과가 크다.
- **주석의 세로 범위는 이웃 악기와의 중간선으로 잘라야 한다.** 넉넉히 잡으면
  아래 시스템의 지시까지 끌어온다. 실제로 Rhythm 2마디에 다음 시스템의
  `Distortion`이 붙어, 원래 있어야 할 `Delay`를 덮어쓰고 있었다.
- **P.M.·let ring은 점선 괄호가 구간을 나타낸다.** 괄호는 글자 바로 위
  가로선으로 그려지고, 같은 줄에 여러 개가 있어도 사이가 뚜렷이 벌어져
  있어서 글자 오른쪽에서 가장 먼저 시작하는 선을 고르면 된다.
  구간 처리를 넣으니 팜뮤트가 74 → 466개가 됐다.
- **밴딩 표기는 목표음 위에 적힌다.** 그런데 그 목표음은 시작음에 병합돼
  사라지므로, 가장 가까운 음을 고르면 뒤쪽 엉뚱한 음(데드 노트 등)에 붙는다.
  표기보다 **앞에 있는, 실제로 칠 수 있는 마지막 음**이 밴딩의 시작음이다.
- **GP는 슬라이드의 도착 프렛을 저장하지 않는다.** 같은 현의 다음 음이 곧
  도착점이라, 이어지는 음이 없는 현에 걸면 갈 곳 없는 슬라이드가 된다.
  다음 음이 같은 현에 있을 때만 걸어야 한다(151 → 102개로 걸러졌다).
